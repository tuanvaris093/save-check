## 3. คำถามและ wording ที่ใช้ทำ P1/P4

ชุดคำถาม 30 รายการและแหล่งเสียง 8 รายการใช้ [ภาคผนวก A ของ Requirements](./REQUIREMENTS_V3.md#ภาคผนวก-a-เนื้อหาแบบประเมินใหม่) โดยคงลำดับที่บันทึกไว้ รุ่นใหม่ใช้ ID คงที่แยกจากรุ่นเดิม เช่น health-light-v3/q1 ไม่ย้ายคำตอบ q1 เก่าไป q1 ใหม่โดยอัตโนมัติ

ถ้อยคำพร้อมนำไปใช้ถูกตรึงใน [health-questionnaire.json](./catalogs/health-questionnaire.json): แสง 10 คู่ beforeText/afterText เสียง 10 ข้อ และความร้อน 10 ข้อ ใช้ JSON นี้เป็นแหล่งข้อความในการ implement เพื่อไม่ต่อคำแล้วผิดไวยากรณ์หรือเปลี่ยนความหมายระหว่างหน้า

คำนำหน้าแบบประเมิน: “กรุณาตอบอาการก่อนและหลังปฏิบัติงาน/เรียนให้ครบทุกข้อ” Tabs “ก่อนปฏิบัติงาน/เรียน” และ “หลังปฏิบัติงาน/เรียน” คำตอบเรียง “ไม่เคย / บางครั้ง / เป็นประจำ” ค่า 0/1/2 ไม่มี preselected answer

เสียงและความร้อนใช้หัวข้อตัวหนาและคำถามครบตามภาคผนวก A; เพิ่ม “ไม่ได้สัมผัสเสียงดังจากแหล่งข้างต้น” เป็น none ที่เลือกพร้อมแหล่งอื่นไม่ได้ เพื่อให้ required ไม่บังคับตอบแหล่งเสียงที่ไม่เกิดขึ้น โดย none ไม่ใช่คะแนนและไม่ทำให้คำถามอาการถูกข้าม

Label ผลสุขภาพใช้ “ระดับอาการตามแบบประเมิน: ต่ำ / ปานกลาง / สูง” ตามช่วงคะแนนเดิม ลดการสรุปว่าไม่มีความเสี่ยงหรือปลอดโรคจากคะแนนอย่างเดียว ผลต่างใช้ “อาการเพิ่มขึ้น / ไม่เปลี่ยนแปลง / อาการลดลง” และแสดงแยกจากระดับอาการ

### 4.3 เสียง

แหล่งกติกา: `sound-standard-2560.pdf` ตารางหน้า 2 และหมายเหตุ. รองรับวิธีประเมินแยกกันเพื่อไม่แปลงเวลาเป็น 8 ชั่วโมงซ้ำ:

1. `exposure-duration`: รับระดับเฉลี่ยที่เป็นตัวแทนการสัมผัสตลอดช่วงและระยะเวลาสัมผัสจริง ใช้ threshold ตาม duration ที่ตรงตารางก่อน หากไม่มี duration ตรงใช้ `L_limit = floor(85 + 3 × log2(8 / hours))` ซึ่งเป็นการจัดรูปจากสูตรใน PDF; เก็บ raw/computed threshold/source. เปรียบเทียบค่าที่วัดจริงกับ threshold ไม่ floor ค่าที่วัดเพื่อให้ผ่าน
2. `twa8`: รับค่า normalized 8-hour TWA ที่รายงานจากวิธีวัดที่ถูกต้องและเทียบ ≤ 85 dBA; ไม่ใช้เวลาสัมผัสมาปรับ threshold อีกครั้ง
3. ค่า min/max หรือ arithmetic mean ของจุดสำรวจพื้นที่ไม่ใช่ค่าที่ใช้แทน exposure TWA โดยอัตโนมัติ หากมีแต่ค่าพื้นที่ให้รายงานข้อมูลไม่พอสำหรับการประเมินนี้ ไม่บันทึกเป็น completed pass/fail

| N06 | duration 0 หรือมีแต่ค่า area avg | validation/insufficient data ไม่ออกผลผ่าน |

ขอบเขตการประเมินนี้เป็นค่าเฉลี่ยการสัมผัสตามตาราง ไม่อ้างว่าครอบคลุม peak/impulse noise หรือ hearing diagnosis ซึ่งต้องมีตัวแปรคนละชนิด

### 4.4 ความร้อน

**แทนที่โดย D48 (16 ตุลาคม):** คืนชุด field และลำดับกรอกตามฟอร์มเดิม ไม่มีตัวเลือกวิธีรับค่า/เพิ่มช่วงวัด และไม่บังคับการกรอกทุกครั้งให้ครบ 120 นาที เก็บ DB/WB/GT, WBGT จากเครื่อง, ค่าเฉลี่ย และเกณฑ์แยกกัน ข้อความโหมด/ช่วงเวลาข้างล่างเป็นแบบออกแบบเก่าของผู้พัฒนา ใช้รองรับข้อมูลที่เคยบันทึกเท่านั้น ไม่ใช้เป็นคำสั่งเพิ่ม UI ดู [ผลตรวจขอบเขต](./REQUEST_SCOPE_AUDIT.md)

แหล่งกติกา: `มาตรฐานความร้อน.pdf` นิยามหน้า 1 และเกณฑ์หน้า 2. ในร่ม/นอกอาคารไม่มีแดด `WBGT = .7 × natural WB + .3 × GT`; มีแดด `.7 × natural WB + .2 × GT + .1 × DB`. ภาระงาน light/moderate/heavy ใช้ 34/32/30 °C ตามลำดับ. ใช้ค่าเฉลี่ยช่วงสองชั่วโมงที่มี WBGT สูงสุดตามนิยามในเอกสาร ไม่ใช้ค่าเฉลี่ยอุณหภูมิอากาศทั่วไป

โหมด meter_average รับ WBGT เฉลี่ยจากเครื่องของช่วงดังกล่าวพร้อมเวลา; โหมด calculated_intervals รับ temperatures กับระยะเวลาของแต่ละช่วง แล้วหาค่าเฉลี่ยถ่วงน้ำหนักตามเวลา ให้ช่วงรวม 120 นาที. ไม่บังคับกรอกค่าเฉลี่ยและ raw อุณหภูมิซ้ำกันในโหมดเครื่องวัด; source และ context ของเวลาต้องอยู่ใน report

| Fixture | Input | Expected |
| --- | --- | --- |
| T01 | ไม่มีแดด WB=28 GT=34 ตลอด 120 นาที, งานเบา | WBGT 29.8 ≤ 34 ผ่าน |
| T02 | มีแดด WB=28 GT=40 DB=35 ตลอด 120 นาที, งานหนัก | WBGT 31.1 > 30 ไม่ผ่าน |
| T03 | WBGT 30 นาน 30 นาที และ 34 นาน 90 นาที | average 33; งานปานกลางไม่ผ่าน (ห้ามเฉลี่ยสองค่าเป็น 32) |
| T04 | meter average 32 งานปานกลาง | ผ่านที่ equality |
| T05 | 32.01 งานปานกลาง | ไม่ผ่านก่อนปัด display |
| T06 | ขาด WB/GT หรือไม่มี DB ในโหมดมีแดด | validation error |

ทุก environmental overall result ผ่านเมื่อทุกหน่วยประเมินผ่าน; unit=จุด Spot/กลุ่มจุดโดยรอบ, พื้นที่ Area, จุด/บริบทเสียง, จุดความร้อน. อัตราจุดผ่านเป็น KPI แยก ไม่เรียกว่า “คะแนนความปลอดภัย” ที่ลบล้าง fail

## 5. Retest เฉพาะไม่ผ่าน และการรักษาผลเดิม

### 5.1 พฤติกรรมที่ต้องใช้

**D54 (16 ตุลาคม) แทนกติกาล็อก metadata เดิม:** แก้ชื่อผู้ตรวจ ตำแหน่ง สถานที่ เครื่องมือ Serial วันที่ปรับเทียบ แผนกและผู้รับผิดชอบได้ในแต่ละรอบ พร้อม snapshot ใหม่ รายการประวัติแสดงชื่อผู้ตรวจของรอบนั้น จุด/เทคนิค/เกณฑ์ยังคงเดิม และผลที่ carry ยังอ้างการตรวจเดิม

1. เปิด latest revision จาก history; server ระบุ eligible failed unit IDs
2. UI แสดงข้อมูลที่ล็อก และช่องกรอกเฉพาะหน่วยที่ไม่ผ่านจาก latest เท่านั้น ไม่ต้องกรอกค่าจุดผ่านใหม่
3. Spot เสริมโดยรอบถือเป็นกลุ่มเดียวกันเมื่อผลกลุ่มไม่ผ่าน; Area ถ้าค่าเฉลี่ยหรือค่าต่ำสุดไม่ผ่านต้องวัดครบจุดย่อยของพื้นที่นั้น เพราะคำนวณค่าเฉลี่ยใหม่จากแค่บางจุดไม่ได้ นี่คือขอบเขตหน่วยไม่ผ่าน ไม่ใช่วัดทุกพื้นที่ของงาน
4. Revision ใหม่มี effective result ของทั้งงาน: จุดที่วัดใหม่ใช้ค่าใหม่; จุดผ่านเดิม carry ผลเดิมพร้อม `carried_from_revision_id`, `measured_at` เดิม และ `observation_kind=carried` ส่วนจุดใหม่เป็น measured
5. Request ต้องมี failed unit set ครบ ไม่อนุญาตตัดจุดที่ไม่ผ่านทิ้ง/เพิ่มจุด/เปลี่ยนเกณฑ์เพื่อให้ผ่าน; server คำนวณ aggregate จาก snapshot ไม่เชื่อคะแนน client
6. ถ้าบางจุดที่เคย fail ผ่านแล้ว รอบถัดไปวัดเฉพาะส่วนที่ยัง fail; เมื่อผ่านทุกหน่วยปิดปุ่ม retest
7. วันเวลาสรุปรอบเป็นวันบันทึกรอบใหม่ แต่ตารางรายจุดต้องแสดงวันวัดจริงของแต่ละจุด; print/export แสดง measured/carried และแหล่ง revision เช่นกัน
8. ค่า remark ของจุดที่ carry คงเดิม; จุดที่วัดใหม่มีหมายเหตุ optional โดยไม่นับเป็นการแก้ metadata ที่ล็อก ไม่มีการบังคับเติมข้อความ
9. Point count/standard/context changes รวมเครื่องมือใหม่หรือเปลี่ยนเวลาสัมผัสเสียงจนเกณฑ์เปลี่ยน ต้องเปิดงานใหม่หรือ correction ที่มี audit ตามขอบเขต ไม่ใช้ retest ปกติ

### 5.2 ตัวอย่างรับงาน

| รอบ | จุด A | จุด B | จุด C | ผลรวม |
| --- | --- | --- | --- | --- |
| r1 | ผ่าน วัดวันที่ 1 | ไม่ผ่าน วัดวันที่ 1 | ไม่ผ่าน วัดวันที่ 1 | ไม่ผ่าน |
| r2 | carry r1 วันที่ 1 | ผ่าน วัดวันที่ 2 | ไม่ผ่าน วัดวันที่ 2 | ไม่ผ่าน |

รหัสงานและจำนวนจุดเท่าเดิม; r2 รับ payload B+C เท่านั้น, r3 รับ C เท่านั้น; r1/r2 เปิดดูได้เหมือนเดิม. การส่งซ้ำ idempotency เดิมไม่เพิ่ม revision; concurrent base mismatch → 409 โดยไม่ทิ้ง draft

## 6. Legacy การแก้ไข และการเก็บเข้าคลัง

- Migration snapshot ข้อมูลเดิมเป็น revision 1 พร้อม `legacy` และค่าที่มีจริง ไม่สร้างก่อน/หลังหรือ metadata สมมติ
- ก่อน retest งานเก่าที่ข้อมูลหลักใหม่ขาด ให้เปิด “เติมข้อมูลประกอบสำหรับการตรวจซ้ำ” ครั้งเดียว บังคับเฉพาะช่องที่ขาดและที่ผู้ตรวจทราบจริง เก็บ audit ของ before=null/after/เวลา/ผู้กรอกที่ระบบมี
- เก็บ metadata supplement แยกจาก snapshot เก่า; revision ใหม่อ้าง supplement version ส่วนรายงานเก่าแสดงข้อมูลตามเวลานั้นและลิงก์เหตุการณ์เติมข้อมูล ไม่แต่งว่าข้อมูลมีมาตั้งแต่ครั้งแรก
- หากไม่ทราบข้อมูลที่ required จริง ให้คงงานเดิมอ่านได้ และให้เริ่มงานใหม่ที่ข้อมูลครบ; ห้ามกรอกตัวเลขเดาเพื่อข้าม validation
- Correction หลังส่ง: ค่าการวัดที่เปลี่ยนต้องเป็น revision แก้ไขแบบมีเหตุผลจำเป็นและ before/after trace ไม่ใช้ generic PATCH ลบ child records; ข้อความเหตุผลของ correction เป็นข้อมูลธุรกรรมที่จำเป็น ไม่ใช่ช่องหมายเหตุทั่วไป
- Metadata ที่ retest ล็อกยังล็อก; หากแก้ metadata ผิดของงานเดิม ให้ใช้ action correction แยกที่แสดงประวัติและไม่ rewrite snapshot เก่า ถ้ากระทบ point topology/standards ให้สร้างงานใหม่อ้างงานเดิม
- ปุ่มลบเปลี่ยนเป็นเก็บเข้าคลัง: ซ่อนจาก default dashboard/export, มี archive filter/restore และแสดงสถานะ archive; ห้าม retest งาน archived จน restore
- ไม่ลบไฟล์ที่ revision ใดอ้างอยู่ ไม่ cascade delete history; policy ลบถาวรไม่อยู่ใน release นี้
- old client PATCH ไปงานที่ใช้ revision แล้วต้อง reject พร้อมข้อความให้อัปเดตหน้า ไม่เปิดช่อง overwrite ผ่าน payload เก่า

## 7. ผังพื้นที่และข้อจำกัด storage

อัปเดต D17 หลัง UAT (14 ต.ค. 2026): แผนผัง optional ทั้ง UI/API/DB; เลือกและดูตัวอย่างในเครื่องก่อนทบทวนและยืนยันแล้วจึงส่ง upload API; เพิ่มภายหลังได้โดยคงประวัติ ดู [งานปรับล่าสุด](./POST_UAT_UI_REPORT.md)

UI ปัจจุบันรับไฟล์ 10 MiB แต่เก็บ base64 ใน D1; [D1 จำกัด string/BLOB/row ที่ 2,000,000 bytes](https://developers.cloudflare.com/d1/platform/limits/) จึงไม่สามารถรับรองไฟล์เต็มขนาดตาม UI ด้วยการออกแบบเดิม

แนวทาง P1/P2: ใช้ R2 สำหรับไฟล์ผังและ D1 สำหรับ file metadata/reference; Worker รับ upload ตรวจชนิด/ขนาดและคืน file ID. ใช้ key ใหม่ต่อไฟล์ ไม่เขียนทับ key ที่ revision เก่าใช้อยู่; เก็บ checksum, byte size, MIME, name. อ้างอิง [R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)

การ upload R2 กับ D1 ไม่ใช่ transaction เดียว: อัปโหลดเป็น staged object ก่อน จากนั้น D1 commit reference; ถ้า DB ไม่สำเร็จเก็บสถานะ orphan สำหรับ cleanup ที่ตรวจว่าไม่มี revision อ้าง ห้ามลบไฟล์เก่าจากการ retry. ถ้า R2 binding ยังไม่พร้อม ให้ไม่เปิด upload v3 ที่บอกว่าสำเร็จ; P9 ตรวจ environment readiness จริง

PDF มาตรฐานเป็น public static assets ไม่มีการย้ายไป R2 ที่จำเป็น ไม่เพิ่มระบบสมาชิกใหม่ใน P0; สิทธิ์อ่าน/เขียนของ API ต้องรักษานโยบายการเข้าถึงของ deployment จริงและไม่ถือว่า CORS เป็น auth

## 8. Flow สำหรับพัฒนา UI เดิม

```text
หน้าแรก
  ประเมินสภาพแวดล้อม → แสง / เสียง / ความร้อน / ความพึงพอใจกลุ่มสภาพแวดล้อม
  ประเมินอาการทางสุขภาพ → แสง / เสียง / ความร้อน / ความพึงพอใจกลุ่มสุขภาพ

สุขภาพแสง
  ข้อมูลบุคคล → งาน/หลักสูตร/ชั้นปี → [ก่อน 10 ข้อ | หลัง 10 ข้อ] → ทบทวน → ผล
  ขั้นประเมิน: ข้อมูลชั่วโมงวันนี้อยู่นอกคะแนน; ก่อนครบจึงถัดไปหลัง
  ย้อน tab/step แล้วข้อมูลอยู่ครบ; แก้ก่อนแล้วคำนวณ delta ใหม่ ไม่ล้างหลัง

สุขภาพเสียง
  ข้อมูลบุคคล → งาน/หลักสูตร/ชั้นปี → แหล่งเสียง → อาการ 10 ข้อ → ทบทวน → ผล
สุขภาพความร้อน
  ข้อมูลบุคคล → งาน/หลักสูตร/ชั้นปี → อาการ 10 ข้อ → ทบทวน → ผล

สภาพแวดล้อมครั้งแรก
  ข้อมูลตรวจ+เครื่องมือ+ผัง → เทคนิค/เกณฑ์/ค่าตรวจ → ทบทวน → ผลล่าสุด
ตรวจซ้ำ
  History → งานไม่ผ่าน → ตรวจซ้ำ → ข้อมูลเดิมล็อก+เฉพาะหน่วยไม่ผ่าน
  → ค่าตรวจ/วันเวลาใหม่ → ทบทวน (แสดงจุด carry) → บันทึก revision → ผลล่าสุด+ประวัติ

ความพึงพอใจสุขภาพ
  ชื่อ/ประเภท/หลักสูตร/ชั้นปี → 16 คะแนน+ข้อเสนอแนะ optional → ทบทวน → ผล
ความพึงพอใจสภาพแวดล้อม
  ชื่อ → 16 คะแนน+ข้อเสนอแนะ optional → เวลาเดิม/แอปกรอกเอง → ทบทวน → ผล
```

ทุกเส้นทางมี back ที่กลับกลุ่มถูกต้อง, required error focus ไปช่องแรก, local draft มี version และ mode. Submit สำเร็จเมื่อ Worker ยืนยัน; network error คง draft ไม่ส่งไปหน้าผลที่แสร้งว่าสำเร็จบน server

## 9. Gate ก่อนส่งต่อ

P0 ปิดได้เมื่อบันทึกคำตอบเจ้าของงานครบ, มี catalog/field matrix/scoring examples/flows/legacy policy, baseline ถูกตรวจจริงและมีรายการข้อจำกัด ใน P1 ให้สร้าง fixtures จากตาราง H/S/L/N/T และ retest example ก่อน implementation evaluator/migration และตรวจรายละเอียด catalog จาก PDF ต้นฉบับ

สิ่งที่ P0 ไม่รับรอง: migration บน production, runtime Worker API, correctness ของข้อมูลวัดจริงจากเครื่องมือ, หรือว่า static/type checks แทน UAT ได้ การตรวจพวกนี้มี phase รับผิดชอบแล้ว
